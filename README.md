# BUILDHIVE Flutter customer app

The Flutter client is organized into maintainable files and is designed around the supplied 23-screen BUILDHIVE flow.

## Setup

1. Install Flutter stable and Android Studio/Android SDK.
2. From this directory, generate platform folders if they are not present:

   ```powershell
   flutter create --platforms=android,ios --project-name buildhive .
   ```

3. Install packages:

   ```powershell
   flutter pub get
   ```

4. Paste your Supabase project URL and publishable/anon key into `lib/config/supabase_config.dart`. Never use a service-role key in the app. Alternatively, pass the values as `--dart-define` overrides.

   ```powershell
   flutter run
   ```

5. Run tests and static analysis:

   ```powershell
   flutter analyze
   flutter test
   ```

Before testing orders or live inventory, run `scripts/checkout_stock_and_address.sql` once in the Supabase SQL Editor. It enables product Realtime, adds the Bohol delivery columns, and installs the atomic `place_order_with_stock` checkout and `cancel_cod_order` cancellation RPCs. Barangay choices load from the official PSGC API after selecting a Bohol municipality.

### Live product catalog

The customer app reads the catalog from `public.products`; it does not use a hard-coded product list. The configured Supabase project currently has 36 active products, and the catalog rows include product image URLs. `Backend.productsStream()` displays rows where `is_active = true` and resolves their category using `category_id`.

The app's product schema contract is:

| Table | Column | Type / purpose |
| --- | --- | --- |
| `categories` | `id` | UUID primary key |
| `categories` | `name` | Category name |
| `products` | `id` | UUID primary key, generated by the database |
| `products` | `name` | Product name |
| `products` | `slug` | URL-safe product identifier |
| `products` | `description` | Product details |
| `products` | `price` | Numeric price in PHP |
| `products` | `stock_quantity` | Integer inventory count |
| `products` | `category_id` | UUID referencing `categories.id` |
| `products` | `is_active` | Boolean; set to `true` to show the product in the app |
| `products` | `unit` | Selling unit, such as `piece`, `bag`, or `cubic` |
| `products` | `image_url` | Optional public URL from the `product-images` bucket |

To add products, insert rows into `public.products` with an existing category ID, verified price and stock, and `is_active = true`. Only Supabase catalog rows are shown in the customer app; do not seed demo prices or stock into the live inventory. Run `scripts/checkout_stock_and_address.sql` once if product changes should arrive through Supabase Realtime. Product image storage setup is documented below.

### PayMongo payments

For a live deployment, run or re-run `scripts/checkout_stock_and_address.sql`, then run `scripts/paymongo_order_lifecycle.sql` in the Supabase SQL Editor. The checkout SQL now deduplicates order creation; the lifecycle SQL adds session tracking and atomic RPCs for payment recording and inventory release.

Set these secrets in **Supabase Dashboard → Edge Functions → Secrets**. Do not place their values in source control or share them in chat:

- `PAYMONGO_SECRET_KEY`: your live PayMongo secret key (`sk_live_...`).
- `PAYMONGO_WEBHOOK_SECRET`: the signing secret shown when you create the live PayMongo webhook endpoint. It is not the API secret key.
- `PAYMONGO_MODE`: exactly `live`.
- `PAYMONGO_CLEANUP_SECRET`: a long random value used only to authorize the scheduled cleanup function.
- `PAYMONGO_PAYMENT_METHOD_TYPES`: optional comma-separated payment methods enabled on your PayMongo account. The default is `card,gcash,qrph`; set it to `card,gcash,qrph` to explicitly enable QR Ph at checkout.

`PAYMONGO_PUBLIC_KEY` is not used by hosted checkout. Supabase injects its project URL and server-side key into Edge Functions; the code supports both legacy service-role and current secret-key environment variables.

In **Edge Functions → Deploy a new function → Via Editor**, create each function using the matching file in `supabase/functions/` and deploy it. Keep **Verify JWT** on for `create-paymongo-checkout`; turn it off for `paymongo-webhook` and `expire-paymongo-checkouts`. PayMongo authenticates its webhook by signature, while the cleanup endpoint checks `PAYMONGO_CLEANUP_SECRET`.

The cleanup worker explicitly expires unpaid Checkout Sessions after 60 minutes, confirms they are expired with PayMongo, and only then restores stock. It runs every five minutes. The schedule SQL enables `pg_cron` and `pg_net`; enable Vault in the Dashboard and store these values there under the exact names shown:

- `buildhive_supabase_url`: `https://<project-ref>.supabase.co`
- `buildhive_supabase_publishable_key`: the Supabase publishable/anon key used by the app
- `buildhive_paymongo_cleanup_secret`: the same value as the `PAYMONGO_CLEANUP_SECRET` Edge Function secret

If you use the SQL Editor instead of the Vault UI, create those Vault entries with the following statements, replacing both placeholders locally and never committing the real cleanup secret:

```sql
select vault.create_secret(
   'https://<project-ref>.supabase.co',
   'buildhive_supabase_url'
);

select vault.create_secret(
   '<Supabase publishable/anon key>',
   'buildhive_supabase_publishable_key'
);

select vault.create_secret(
   '<same value as PAYMONGO_CLEANUP_SECRET>',
   'buildhive_paymongo_cleanup_secret'
);
```

Then run `scripts/schedule_paymongo_checkout_cleanup.sql` in the SQL Editor. Check the Cron job run history after deployment. If PayMongo reports that a payment is in progress, cleanup leaves the stock reserved and retries on the next run.

Register this HTTPS endpoint in PayMongo and subscribe it to `checkout_session.payment.paid`:

```text
https://<project-ref>.supabase.co/functions/v1/paymongo-webhook
```

Subscribe the endpoint to `checkout_session.payment.paid` in live mode. The webhook verifies the raw-body HMAC signature, session ID, currency, mode, and amount before updating the order. A payment arriving after stock release is recorded with `payment_review_required = true`; review and fulfill it if stock is available, otherwise refund it from the PayMongo Dashboard. Start with a low-value live transaction only after confirming the project, secrets, webhook delivery, and Cron job.

### Product images

1. Run `scripts/product_images_storage.sql` in the Supabase SQL Editor. It creates a public-read `product-images` bucket with a 5 MB file limit and JPEG, PNG, and WebP allowlisted.
2. In Supabase Dashboard, open **Storage**, enter `product-images`, and upload each product image. Use a unique filename for each image.
3. Copy each file's public URL and save it to that product's `image_url` field in `public.products`.

The customer app displays these URLs directly. Uploads are intentionally limited to the Supabase Dashboard; the client has no product-image upload flow or admin authorization.

## Source layout

- `lib/main.dart`: app bootstrap and Supabase initialization
- `lib/config/supabase_config.dart`: Supabase project URL and client-safe publishable key
- `lib/app.dart`: app theme and root flow
- `lib/core/theme.dart`: BUILDHIVE yellow/charcoal theme
- `lib/core/models.dart`: product model
- `lib/core/services.dart`: catalog/profile backend access
- `lib/features/onboarding/launch_flow.dart`: splash and three onboarding slides
- `lib/features/shell.dart`: bottom navigation shell
- `lib/features/screens.dart`: catalog, product detail, cart, checkout, order tracking, orders, profile, addresses, payment methods, support, settings and authentication

## Important production notes

- The local cart is currently in-memory and clears when the app process is restarted.
- The UI currently uses generic product icon placeholders when no `image_url` is stored in Supabase.
- Order prices and inventory are calculated server-side. Live PayMongo operation depends on applying both payment SQL scripts, deploying all three Edge Functions, configuring live secrets, registering the webhook, and enabling the cleanup Cron job.
- Configure PayMongo secret keys only as Supabase Edge Function secrets. Never store card data or secret keys in the Flutter client.
- Confirm webhook signature validation against the current PayMongo documentation before live deployment.
- Google Maps and live driver tracking require a maps key, billing/configuration, driver app/location source and access rules.
